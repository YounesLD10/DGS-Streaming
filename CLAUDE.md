## Project Overview

**DGS-Streaming** is a real-time payments streaming POC running on Minikube. It processes Powercard Operations CSV files through a 4-stage PyFlink pipeline, storing canonical output in MinIO (S3-compatible). All infrastructure is managed with Terraform and a single orchestration script.

**Target environment:** 16GB RAM machine, 7168MB allocated to Minikube. All resource values are tuned to fit this budget.

## Common Commands

### Full infrastructure lifecycle

```bash
# Bring up everything (Minikube + operators + Kafka + Flink jobs + MinIO)
./setup_poc.sh up

# Produce test data from a CSV file (rate defaults to 20 msg/s)
./setup_poc.sh produce "data/<file>.csv"
./setup_poc.sh produce "data/<file>.csv" 50 200   # rate=50/s, limit=200 rows

# Check pod status across all 3 namespaces
./setup_poc.sh status

# Tear down everything
./setup_poc.sh down
```

### Targeted operations

```bash
# Rebuild and reload the PyFlink Docker image into Minikube
./setup_poc.sh build

# Re-deploy Flink jobs only (after a code change)
./setup_poc.sh jobs
```

### Accessing the Flink UI

Each Flink job runs in application mode with its own JobManager. Port-forward individually:

```bash
kubectl port-forward svc/job1-decryption-rest    8081:8081 -n traitement &
kubectl port-forward svc/job2-validation-rest    8082:8081 -n traitement &
kubectl port-forward svc/job3-normalization-rest 8083:8081 -n traitement &
kubectl port-forward svc/job4-sink-rest          8084:8081 -n traitement &
```

Open `http://localhost:8081` through `http://localhost:8084`.

### Checking job health

```bash
kubectl get flinkdeployment -n traitement          # all 4 jobs, lifecycle + job status
kubectl logs -n traitement <pod-name> -c flink-main-container
```

### Verifying MinIO output

```bash
kubectl exec -n stockage deployment/minio -- mc ls local/rt-payments/canonical/ --recursive
```

## Architecture

### Pipeline (5 Kafka topics, 4 Flink jobs)

```
CSV file
  └─► producer.py (Fernet-encrypt) ──► payments
                                            │
                                     job1_decryption.py
                                      ├─► payments.decrypted
                                      └─► payments.dlq (errors)
                                            │
                                     job2_validation.py (ISO 8583/4217/7812 checks)
                                      ├─► payments.validated
                                      └─► payments.dlq
                                            │
                                     job3_normalization.py (ISO 20022-inspired schema)
                                          └─► payments.normalized
                                                    │
                                             job4_sink.py
                                              └─► MinIO s3a://rt-payments/canonical/
```

### Kubernetes namespaces

| Namespace | Contents |
|-----------|----------|
| `ingestion` | Strimzi operator, Kafka broker + ZooKeeper, all 5 Kafka topics |
| `traitement` | Flink Kubernetes Operator, 4 FlinkDeployments (one per job) |
| `stockage` | MinIO (standalone, ephemeral for POC) |

### Terraform two-stage deploy

The deploy is split into two stages to avoid CRD bootstrap race conditions:

- **`terraform/`** (Stage 1): Namespaces, Strimzi operator, Flink operator, MinIO. Includes `local-exec` CRD wait provisioners that poll until CRDs are Established before completing.
- **`terraform/stage2/`** (Stage 2): Kafka cluster + 5 topics, 4 FlinkDeployment manifests, Fernet secrets. Can only run after Stage 1 because CRDs must exist.

**Important:** The `.tf` files in both `terraform/` and `terraform/stage2/` are **git-ignored** — they are regenerated by `setup_poc.sh` from embedded heredocs on each run. Edit the heredocs in `setup_poc.sh` if you need to change Terraform config.

### Flink application mode (not session mode)

All 4 jobs use **application mode** (`FlinkDeployment` with a `job` section), not session mode. This means:
- Each job has its own JobManager pod, hence its own Flink UI.
- `jarURI = local:///opt/flink/python-driver/flink-python.jar` — the `local://` scheme works because the JM reads from its own container filesystem.
- The jar at that path is a **symlink** to `/opt/flink/opt/flink-python-1.18.1.jar`. The original must stay in `/opt/flink/opt/` because `PackagedProgramUtils.getPythonJar()` scans that directory for exactly one `flink-python*.jar`.

### Docker image (`flink-jobs/Dockerfile`)

Built locally and loaded into Minikube's daemon (`eval $(minikube docker-env)` + `docker build`). `imagePullPolicy: Never`.

Critical details:
- **S3 plugin:** Uses `flink-s3-fs-hadoop` (not presto). The hadoop variant implements `RecoverableWriter`, which `FileSink` (Sink2 API) requires. The presto variant does not and will fail at stream graph construction.
- **Python driver jar:** Symlinked, not moved. Both the symlink at `/opt/flink/python-driver/flink-python.jar` and the original in `/opt/flink/opt/` must exist simultaneously.
- **MinIO config** is baked into `flink-conf.yaml` in the image (`s3.endpoint`, `s3.path.style.access`, credentials).

### Memory tuning (fits 7168MB Minikube)

Default JVM metaspace (256MB) + overhead (192MB) leaves insufficient Flink memory in small containers. These overrides are set in every FlinkDeployment:

```
jobmanager.memory.jvm-metaspace.size = 128mb
jobmanager.memory.jvm-overhead.min   = 64mb
taskmanager.memory.jvm-metaspace.size = 128mb
taskmanager.memory.jvm-overhead.min   = 64mb
taskmanager.memory.managed.fraction   = 0.2   # Python needs less managed memory
```

Results: JM=768MB → 563MB Flink memory ✓, TM=640MB → 448MB Flink memory ✓. 4 jobs × (768+640)MB ≈ 5.6GB for Flink pods, leaving headroom for Kafka (512MB+256MB), MinIO, and operators.

## Encryption

The pipeline uses **Fernet** (symmetric AES-128-CBC) for payload encryption:
- Key stored in `.fernet.key` at project root (generated once, git-ignored)
- Same key provisioned as a Kubernetes Secret (`fernet-key`) in both `ingestion` and `traitement` namespaces
- Producer encrypts the full row dict → base64 token in `encrypted_payload`
- Job 1 decrypts using `FERNET_KEY` env var (sourced from the secret)

## Common Pitfalls

- **ZooKeeper zxid mismatch after restart:** Ephemeral storage means ZK loses its transaction log on pod restart. If the Kafka broker is still running with a higher zxid, ZK refuses connections. Fix: delete both pods simultaneously — `kubectl delete pod payments-cluster-zookeeper-0 payments-cluster-kafka-0 -n ingestion`.
- **Strimzi operator must be Ready before Kafka manifests are applied.** The script adds a rollout wait; Terraform CRD wait provisioners only check CRD registration, not operator readiness.
- **Terraform state vs. cluster state:** `setup_poc.sh` runs `_tf_import_if_missing()` before each apply to reconcile existing resources into state, avoiding "already exists" errors.
- **Producer runs in a local venv** at `.producer-venv/` (git-ignored). The venv is auto-created on first `produce` invocation. If it becomes corrupted, `rm -rf .producer-venv` to reset.
